# 远控内核输入驱动 / 驱动签名 / ViGEm 集成 —— 技术调研与投入评估

> 纯技术调研文档，**不含任何驱动代码**。目的：在动手前，先把"要不要做内核级远控输入"这件事的
> 技术路线、签名成本、维护负担、风险与替代方案讲清楚，供决策是否立项、投多少。
> 事实部分均经 2026-06 联网核实（来源见文末）。

---

## 0. 一句话结论（先看这个）

对**当前这个企业 RAG-Agent 产品**而言，内核级远控输入**不建议混进现有代码库**。它是一条独立的
C++/内核产品线，需要专门的内核工程师 + EV 证书 + 微软驱动签名资质 + 长期维护，且只在"要对抗游戏
反作弊"这一个特定场景才有不可替代的价值。如果你的远控是给**远程办公/运维/技术支持**用的，现有
WebRTC + Win32 注入栈已经够用，风险也低得多。只有当明确目标是**云游戏/远程游戏陪玩、且必须穿透
反作弊**时，才值得评估这笔投入——而那是一个 6~12 个月、需要专职团队和持续签名维护的独立项目。

---

## 1. 为什么会想要"内核输入"——它解决什么，不解决什么

你现在的输入注入走的是 **Win32 级**（`SendInput` / Electron `sendInputEvent` / Computer Use 驱动经
shell 执行）。它的真实能力边界：

**能做**：操控普通桌面程序（浏览器、Office、IDE、大多数应用），远程办公/运维/演示完全够用。

**做不到 / 受限**：
- **游戏反作弊会拦**：很多带反作弊的游戏（尤其在内核态跑 anti-cheat 的，如 EAC、BattlEye、
  Vanguard）能识别 `SendInput` 这类 User 层注入并拒绝/封号。UU GameViewer 用内核驱动 `gvinput.sys`
  正是为了绕过这一层 User 层检测。
- **安全桌面（Secure Desktop）注入不了**：UAC 提权弹窗、登录锁屏、Ctrl+Alt+Del 安全画面这些
  运行在独立的安全桌面上，普通进程的 `SendInput` 到不了那里（这也是为什么远控登录界面常需要特殊
  处理）。
- **不是"硬件级"输入**：少数游戏/程序会校验输入是否来自真实 HID 设备。

**关键的诚实判断**：内核输入的核心价值就是"绕过 User 层反作弊 + 触达安全桌面 + 看起来像真实
HID"。如果你的场景用不到这三点，内核输入带来的全是成本、没有收益。而即便做了内核注入，**也不是
万能钥匙**——现代反作弊本身也在内核态，能否穿透是一场持续军备竞赛，UU 的 `gvinput` 对很多游戏有效、
但绝不是对所有游戏永久有效。且用于"作弊"违反游戏 ToS，有法律与封号风险。

## 2. 输入注入的四条技术路线（选型对比）

| 路线 | 是什么 | 触达能力 | 成本 / 风险 | 适用 |
|---|---|---|---|---|
| **A. Win32 SendInput / Electron sendInputEvent**（你现在的） | User 层 API 注入 | 普通桌面程序 OK；反作弊/安全桌面不行 | 零额外成本，零驱动维护 | 远程办公/运维/支持 |
| **B. 自研 KMDF 过滤/虚拟 HID 驱动**（UU gvinput.sys 路线） | 自己写内核驱动，做 kbdclass/mouclass 上层过滤 + 虚拟 HID 注入 | 最强，可绕 User 层反作弊、可触达安全桌面 | 最高：自建+签名+长期维护内核驱动 | 云游戏/远程陪玩 |
| **C. Interception 驱动**（oblitum 开源） | 现成的内核键鼠过滤驱动 + C/.NET 库 | 较强（驱动级注入/拦截） | 中：复用现成驱动，但有稳定性与分发签名问题 | 想快速验证内核注入可行性 |
| **D. ViGEm 虚拟手柄**（手柄专用，见 §4） | 虚拟 Xbox/DS 手柄总线驱动 | 手柄输入（非键鼠） | 中：现成签名驱动，但已归档 | 手柄透传/云游戏手柄 |

### 2A. Win32（现状）
不展开——你已经在用，它是兜底，永远保留（UU 自己的降级链最后一环也是回退 `SendInput`）。

### 2B. 自研 KMDF 内核驱动（gvinput.sys 等价路线）
- **技术形态**：用 Microsoft **KMDF**（Kernel-Mode Driver Framework）写一个驱动，通常是
  ① 在 `kbdclass`/`mouclass` 类驱动之上注册 **UpperFilter**（拦截/注入键鼠 IRP），或
  ② 实现一个**虚拟 HID 设备**（让系统以为接了真键鼠），把远端传来的输入喂进去。
- **优点**：完全自主可控、能力最强、能做到"看起来像真实硬件"。
- **代价（这是重点）**：
  - 需要**内核开发能力**——这是稀缺技能，调试是蓝屏级别（一个空指针就 BSOD），不是招个前端/后端
    就能顶上的。
  - 需要走**完整的微软驱动签名流程**（见 §3），每次驱动改动都要重新签、可能重新过测试。
  - 需要**长期维护**：Windows 大版本更新、安全补丁、Secure Boot/HVCI/内存完整性策略变化都可能让
    驱动加载失败，得跟着修。
  - **安全与责任**：内核驱动的 bug = 蓝屏或提权漏洞，企业客户对"装内核驱动"非常敏感（很多企业
    安全基线直接禁止第三方内核驱动）。
- **结论**：能力天花板最高，但这是"做一个驱动产品"的工作量，不是"给 Agent 加个功能"。

### 2C. Interception 驱动（oblitum/Interception）
- **是什么**：开源的 Windows 内核**过滤驱动**，在驱动层拦截/修改/重注入键鼠事件；用设备句柄
  `\\.\interception00 ~ 99` 管理设备，提供 C 库 API（`InterceptionStroke` = 键/鼠 stroke），社区还有
  .NET 封装（NuGet 上的 `InputInterceptor`，.NET Standard 1.3+，自带驱动安装器）。
- **优点**：现成、有 C/.NET 绑定，能较快验证"内核级注入"是否解决你的问题，不必从零写驱动。
- **风险/坑（核实到的真实问题）**：
  - 它是 **kbdclass 的上层过滤驱动**——装不好/程序卡死会**直接锁死键鼠**（社区有"装完重启后键鼠
    在安全模式都用不了"的 issue），生产环境风险高。
  - **分发与签名**：你是在你的安装包里**搭载别人的内核驱动**，要处理它的签名、版本、与用户机器上
    已有 Interception 的冲突，以及企业环境对未知内核驱动的拦截。
  - 它的设计初衷偏"拦截/改键"（如改键、宏），把它当"远程注入后端"是借用，不是它的主场。
- **结论**：适合做**可行性验证**（花几天确认内核注入能不能解决你的具体反作弊场景），不建议直接当
  产品后端长期依赖。

## 3. 驱动签名流程与成本（做内核驱动绕不过的关）

> 这是"自研驱动"或"搭载第三方内核驱动公开分发"都必须面对的部分，也是很多人低估的成本。

**硬性事实（Win10 1607 起，已核实 2026-06）**：
1. **内核驱动必须由微软签名才能在现代 Windows 加载**——自签/测试签名只能在开了测试模式的机器上跑，
   不能给普通用户用。
2. **必须有 EV（Extended Validation）代码签名证书**——注意：**连注册微软 Partner Center
   （Hardware Dev Center）账号都需要先有 EV 证书**。EV 证书：
   - 向 CA（如 DigiCert/SSL.com/GlobalSign 等）购买，**约 $300~$600/年**起，多年更便宜；
   - 私钥必须存在**硬件令牌/HSM**里（不能导出），有的 CA 用云 HSM；
   - 申请要做**企业身份验证**（邓白氏编号/工商信息等），通过要**数天到数周**。
3. **签名方式两种**：
   - **Attestation signing（证明签名）**：用 EV 证书把驱动打成 CAB、提交到 Partner Center → 微软盖章。
     支持 **Win10+ 桌面**的内核/用户态驱动。证书必须 SHA-2、`/fd sha256`，提交时**两个 test-signing
     选项都不要勾**。这是最常走的路。
   - **WHQL / HLK 认证签名**：要兼容更老的 Windows 或拿完整认证，得跑 **HLK（Hardware Lab Kit）测试
     套件**，流程重得多。**核实到的现状**：HLK 测试项在扩张、即便很小的驱动更新也常要**整套重测、
     重新提交**，"以前几小时、现在动辄数周"，文档晦涩、Partner Center 报错难懂。
4. **维护负担**：驱动每次改动→重签；Windows 更新可能要重新认证。

**成本小结**：EV 证书 $300~600/年 + 注册/认证的人力与时间（首次数周）+ 每次发版的签名/可能重测
+ 专职内核工程师工资。这不是一次性投入，是**持续投入**。

## 4. ViGEm 集成（手柄方向，云游戏才需要）

如果远控目标里有"把控制端的手柄透传给被控端的游戏"，对应的是 **ViGEm（Virtual Gamepad Emulation）**：

**现状（已核实 2026-06，有重要变化）**：
- **ViGEmBus 已于 2023-11-02 归档/退役**（与 ViGEM GmbH 的**商标冲突**，非技术原因），不再更新，
  最后驱动版本 **v1.16.x**。但**仍可正常使用**、由 Nefarius（Benjamin Höglinger-Stelzer）数字签名，
  DS4Windows、DualSenseX 等主流工具仍在用它。
- **后继项目 `VirtualPad` 正在开发中**（接棒 ViGEmBus）。
- **托管库 `ViGEmClient` 在 NuGet 上**（Nefarius 账号，.NET Standard 2.0），C/C++ 也有绑定。
- **技术形态**：基于微软 **KMDF** 的内核驱动，模拟 **Xbox360 / XboxOne / DS3 / DS4 / DualSense**；
  关键优点是**纯软件设备、游戏无需改动即可识别**（无需 Proxy-DLL / API-Hook）。
- **配套**：`HidHide`（隐藏物理手柄，避免和虚拟手柄冲突）、`BthPS3`（PS3 手柄蓝牙连接），都是
  Nefarius 系。
- **⚠️ 安全提醒（务必注意）**：旧版 ViGEmBus 的自动更新器会联系一个**已过期的域名**，从 2024 年起
  谁拿到该域名就可能**拿到用户公网 IP**。Nefarius 出了 **`Legacinator`** 工具修这个问题。若你打算
  搭载/依赖 ViGEm，必须用新版、并关掉/修正旧更新器逻辑。

**集成形态（不写代码，只说形态）**：在被控端搭载 ViGEmBus 驱动（已签名）+ 通过 ViGEmClient（托管库
或原生）创建虚拟手柄，把控制端经协议传来的手柄状态喂给虚拟手柄。**注意它仍是内核驱动**，§3 的签名/
分发/企业拦截问题同样适用（虽然 ViGEmBus 本身已签名，但你在安装包里搭载它、保证版本与安全更新仍是
你的责任）。

## 5. 各路线落到"我们这个产品"的投入/风险评估表

| 维度 | A. Win32(现状) | B. 自研内核驱动 | C. Interception | D. ViGEm 手柄 |
|---|---|---|---|---|
| 工程量 | 0（已有） | 极大（内核产品级） | 中（集成现成驱动） | 中（集成现成驱动） |
| 关键技能 | 无 | 稀缺的内核工程师 | C/.NET + 驱动分发 | C/.NET + 驱动分发 |
| 证书/签名 | 普通代码签名即可 | **EV + 微软认证，持续** | 搭载他人内核驱动的签名/分发 | ViGEm 已签，但搭载/更新是你的责任 |
| 首次时间 | — | 6~12 个月 | 数天验证 / 数周产品化 | 数周 |
| 持续维护 | 低 | 高（跟 Windows 更新） | 中 | 中（且原项目已归档） |
| 企业接受度 | 高 | 低（很多企业禁第三方内核驱动） | 低 | 中低 |
| 反作弊有效性 | 低 | 高但非永久（军备竞赛） | 中高 | 手柄场景适用 |
| 法律/ToS 风险 | 低 | 用于绕反作弊有风险 | 同 B | 较低 |

## 6. 建议（分场景）

- **场景一：远控是给远程办公/运维/技术支持用的**
  → **不做内核**。保持现有 WebRTC + Win32 注入。把精力放在**已经能做、且纯逻辑可验证**的体验升级上：
  自适应码率（已做）、多屏切换、双向剪贴板、会话录制、断线重连、画质统计面板（本轮在做）。这些才是
  企业远控用户真正每天用得到的，且零内核风险。

- **场景二：明确要做云游戏/远程陪玩，且必须穿透反作弊**
  → 这是**独立立项**。先用 **Interception（路线 C）花几天做 PoC**，确认对你的目标游戏/反作弊是否
  真的有效（别先投半年再发现穿不透）。PoC 通过且商业上确实值得，再评估**自研 KMDF 驱动（路线 B）+
  EV 证书 + 专职内核团队**的长期投入；手柄部分搭载 **ViGEm/VirtualPad（路线 D）**。**强烈建议**把它
  做成**独立的可选组件/独立产品**，与当前 Agent 主程序解耦——既隔离内核风险，也方便企业版关闭。

- **无论哪种**：保留 Win32 兜底（UU 自己最后一环也是 `SendInput`）。

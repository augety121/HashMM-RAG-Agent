# HashMM 未来路线图：从 RAG-Agent 到自主智能体（V206 前瞻规划）

这份文档回答一个战略问题：**项目下一步往哪走。** 你的直觉是对的——主流正在从"RAG 问答"转向"Agent 干活"，RAG 会退化成 Agent 的一个可拆卸能力模块，而 Agent 本身在向"理解意图、自主规划、高质量交付"演进。本文把这个方向拆成可执行的阶段。

写作原则：只写有依据的判断，不做无根据的预测。每个阶段都对应你仓库里**已有的地基**，说明"从哪改"，而非空想。

---

## 一、核心判断：RAG 是 Agent 的一个工具，不是架构中心

**现状认知纠偏**：很多人（包括早期的你）把项目理解为"一个 RAG 系统 + 一些 Agent 功能"。正确的心智模型应该反过来——**项目是一个 Agent，RAG 是它众多工具能力中的一个**（`kb_search`）。

证据在你自己的代码里：`agent/loop.py` 的 ReAct 循环里，`kb_search` 和 `fetch_url`、`web_search`、`spawn_worker`、`create_file` 是平级的工具。Agent 根据任务决定要不要检索——纯写作任务根本不调 RAG。这说明架构上 RAG 已经是"可选工具"，只是叙事上还没转过来。

**为什么这个判断重要**：它决定了模块边界。RAG 应该能被**整体拔掉**而不影响 Agent 主循环——这样才能：① 出问题时快速定位（是检索坏了还是循环坏了）；② 做纯 Agent 场景（Computer Use、代码任务）时零 RAG 开销；③ 未来 RAG 范式若被取代（如长上下文吞掉检索），拔掉即可，不用重构 Agent。

---

## 二、阶段划分

### 阶段 A：模块化解耦（近期，工程为主）——让 RAG 可插拔

**目标**：把 RAG 从"嵌在检索桥里的必需品"变成"注册进 Agent 的一个工具插件"，可通过开关整体启停。

你已有的地基：
- `retriever_bridge.kb_search_bridge` 已是独立函数，`retrieval_pipeline` 已是独立管线。
- `hooks.py` / `user_hooks.py`（本轮新增）已有工具注册机制。
- `feature_flags.py` / `feature_presets.py` 已有特性开关框架。

要做的：
1. **定义 `ToolModule` 协议**：每个能力（RAG / Computer Use / Browser Use / 代码执行）实现统一接口 `{name, schema, execute, health, enabled}`，注册进一个 `ToolRegistry`。RAG 成为其中一个模块。
2. **一个开关拔掉 RAG**：`HASHMM_MODULE_RAG=0` 时，Agent 工具列表里不出现 `kb_search`，检索管线不初始化，Agent 照常跑纯推理/Computer Use 任务。
3. **模块级健康检查与降级**：每个模块自带 `health()`，某模块挂了只禁用该模块（返回"该能力暂不可用"），不拖垮整个 Agent。对应你"出了问题可以定位"的诉求——模块边界就是故障边界。

产出价值：面试时可讲"我的架构是 Agent-centric，能力模块化可插拔，RAG 只是注册进来的一个工具，可整体拔除"——这是比"我做了个 RAG"高一个层次的叙事。

### 阶段 B：意图理解与主动澄清（中期）——从"执行命令"到"理解意图"

**目标**：Agent 不止执行字面任务，而是先理解用户**真正想要什么**，不确定时主动澄清，而非猜错方向跑一大圈。

你已有的地基：
- `query_planner.py`（查询规划）、`intent_engine`（意图识别）、`evolution/user_model.py`（用户画像个性化）。
- `loop.py` 已有 DoD 自检（宣布完成但清单没做完会打回）。

要做的：
1. **意图分层**：把用户输入解析成"表层请求 / 深层目标 / 隐含约束"三层。例：用户说"整理下载文件夹"，深层目标是"找到我要的文件"，隐含约束是"别删我还要的东西"——所以要先列出重复项让用户确认（你的 `seq` 任务已在做，把它规范成通用能力）。
2. **主动澄清阈值**：当意图置信度低于阈值时，不硬跑，先问一个关键澄清问题（`ask_user` 工具）。关键是**只在真正模糊时问**，不啰嗦——大厂的体验分水岭就在这里。
3. **用户画像驱动的默认值**：`user_model` 记住用户偏好（喜欢表格/简洁/带出处），把这些作为任务的隐含约束自动注入，不用每次都说。

### 阶段 C：自主规划与高质量交付（中期偏后）——从"完成"到"完成得好"

**目标**：把一个模糊任务自主拆成计划、执行、自检、修正，交付**高质量**结果而非"能跑就行"。

你已有的地基（这块你其实做得不浅）：
- `loop.py` 已有：verify-fix（生成代码自动编译校验、失败重来）、DoD 自检、引用接地校验（幻觉引用打回）、`spawn_worker`（子任务派专员）。
- 本轮新增：`user_hooks.on_finish`（回合收尾钩子）、诊断助手（跑挂了自动分析）。

要做的：
1. **计划先行、显式可见**：复杂任务先产出结构化计划（步骤 + 每步验收标准），用户可确认/调整（Plan Mode 已有雏形），再执行。计划本身作为 DoD 的依据。
2. **质量闸常态化**：把 verify-fix / DoD / 引用校验从"代码/RAG 专用"推广成"每类任务都有验收标准"——写文案有文案的验收（是否覆盖要点、语气是否匹配），调研有调研的验收（是否多源交叉）。
3. **失败自愈闭环**：诊断助手（本轮）+ on_finish 钩子 → 任务失败自动分析根因 → 下一轮自动调整策略重试，而非把错误抛给用户。

### 阶段 D：多模态与全场景（远期）——语音入口 + 跨端无感

**目标**：用户用**语音说一句**，Agent 理解 → 规划 → 跨端执行 → 高质量交付，全程无需盯着。

你已有的地基：
- `StreamingSttClient`（App 流式语音）、图片资源库（本轮，图2-④）、Computer Use / Browser Use（客户端侧）。
- 本轮 P2-9 派活队列：任务可派到任意 runner 云上闭环。
- 跨端同步：Supabase 双向同步（App 问的问题同步到桌面）。

要做的：
1. **语音为一等入口**：语音 → 意图理解（阶段 B）→ 规划（阶段 C）→ 执行。不是"语音转文字再当文字处理"，而是语音场景下更主动（因为用户没在看屏幕，更需要 Agent 自己把事想周全）。
2. **多模态检索融合**：图片库接进 mix 检索第五路（当前是文本搜图，未来接 CLIP 做以图搜图），Agent 能理解"上次那张营收图"这类指代。
3. **跨端真正无感**：本轮已修 trace 带 conv_id、派活队列；下一步是"App 说的任务，桌面端实时接管执行，结果回 App"的完整闭环——你 P2-9 的调度层就是为这个铺的路。

## 三、模块化架构的落地形态（阶段 A 的具体设计）

```
┌─────────────────────────────────────────────────────────┐
│                    Agent 主循环 (loop.py)                  │
│         意图理解 → 规划 → ReAct 循环 → 质量自检 → 交付       │
│         （轮数/预算/时限三闸 · 结构化停止 · 回合收尾钩子）    │
└───────────────────────────┬─────────────────────────────┘
                            │ ToolRegistry（统一注册/健康/开关）
        ┌───────────┬───────┼───────┬───────────┬──────────┐
        ▼           ▼       ▼       ▼           ▼          ▼
   ┌─────────┐ ┌────────┐ ┌──────┐ ┌────────┐ ┌────────┐ ┌──────┐
   │ RAG 模块 │ │Computer│ │Browser│ │代码执行 │ │图片检索 │ │ 派活 │
   │kb_search│ │  Use   │ │  Use  │ │ create │ │ image  │ │dispatch│
   │可整体拔除│ │        │ │       │ │ _file  │ │ search │ │      │
   └─────────┘ └────────┘ └──────┘ └────────┘ └────────┘ └──────┘
   每个模块：{name, schema, execute, health, enabled}
   故障边界 = 模块边界；某模块挂了只禁用它，不拖垮 Agent
```

关键点：**RAG 和其它模块完全平级**。这张图就是"RAG 是可拆卸模块"的架构表达——也是你反复强调的"模块化、出问题能定位"的答案。

## 四、给你的执行建议（优先级）

1. **先做阶段 A 的模块开关**（工作量小、收益大）：`HASHMM_MODULE_RAG=0` 能拔掉 RAG，是"模块化"最直接的证明，面试可讲、排障有用。
2. **阶段 B 的主动澄清**是体验分水岭：大厂 Agent 和 demo 的最大差距不在能力，在"懂不懂用户"。一个"不确定就问一句"的机制，体验感提升最明显。
3. **阶段 C 你已完成大半**（verify/DoD/引用校验/诊断），缺的是"推广到每类任务"和"计划显式化"——是整理归纳，不是从零造。
4. **阶段 D 是愿景**，不要提前投入太多，等 A/B/C 扎实了自然水到渠成。避免"为了 AGI 而 AGI"堆功能——你自己也警惕这一点。

---

## 五、一句话总结

> 项目的未来不是"更强的 RAG"，而是"更懂用户、能自主把事做好的 Agent"，RAG 只是它可拆卸的一个工具模块。近期把能力模块化（A）、让 Agent 懂意图（B）、把已有的质量闸推广成通用交付标准（C）；远期做语音入口 + 跨端无感的全场景智能体（D）。每一步都建立在你现有的地基上，不推倒重来。

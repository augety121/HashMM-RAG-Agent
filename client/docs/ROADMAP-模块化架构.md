# HashMM 架构路线图：Agent 为主干，RAG 为可拆卸模块（V203 起）

> 目的：回答三个问题 —— ① 未来功能怎么长（不长成屎山）；② 出了问题怎么一眼定位；
> ③ 我们押注的终局形态是什么、现在的每一步怎么对着它走。

---

## 1. 判断：行业风向与我们的位置

2024 年大家做的是"RAG 产品"：检索是主角，LLM 是润色器。
2025-2026 风向已经明确翻转（Claude Code、Manus、各家 Deep Research 都是同一形态）：

**Agent 是主干，一切能力（包括 RAG）都是它手里的工具。**

- 模型上下文越来越长、越来越便宜 → "把检索片段塞进 prompt"的静态 RAG 价值持续缩水；
- 模型自主多步执行能力越来越强 → 价值从"检索得准"迁移到"任务完成得好"；
- 生态标准（工具协议、Agent Skills / SKILL.md、MCP）在收敛 → 谁的架构模块化，谁能白嫖生态。

HashMM 的既有资产（自建索引、知识图谱、语义缓存、记忆、自我进化）都不作废——
它们从"主干"降级为"挂在 Agent 上的高质量工具"，这恰恰是它们最保值的位置。

## 2. 目标架构：一根主干，四类插槽

```
                 ┌────────────────────────────────────────┐
   语音/文字 ──▶ │  意图理解层（要什么，约束是什么）           │
                 └──────────────────┬─────────────────────┘
                                    ▼
                 ┌────────────────────────────────────────┐
                 │  Agent 主干（hashmm/agent/loop.py）      │
                 │  计划 → 选工具 → 执行 → 反思 → 交付        │
                 └───┬─────────┬─────────┬─────────┬──────┘
                     ▼         ▼         ▼         ▼
                （A）知识插槽（B）行动插槽（C）经验插槽（D）表达插槽
                 kb_search   execute_code  记忆/技能包   create_document
                 kg_query    create_file   经验回放      文件/图表
                 web_search  远程控制      学习型技能    语音播报
```

**插槽纪律（新功能必须遵守，这是防屎山的宪法）：**
1. 每个能力 = 一个工具（清晰的名字 + 参数 + 返回），注册进 `AGENT_TOOLS`，绝不散落在主循环里写 if；
2. 能力失效必须**静默降级**：工具坏了 = Agent 少一件工具，主问答流程照常（V58 技能注入、V203 技能包注入都是这个模式：`try/except log_suppressed`）；
3. 能力自带开关（环境变量或设置项），可单独关掉验证"没有它系统是否还好"—— 这就是"可拆卸"的操作定义；
4. UI 上每个能力必须有入口和状态展示（用户看得见 = 出问题时用户说得清）。

## 3. RAG 的"可拆卸模块化"具体拆法

现状：检索逻辑分布在 chat_retrieval / kg / semcache 等处，与问答主链耦合。
目标：收敛为 4 个独立可关的模块，Agent 通过统一工具面调用：

| 模块 | 工具面 | 独立开关 | 拆掉后的系统行为 |
|---|---|---|---|
| 向量检索 | kb_search(mode=naive) | 索引不存在即自动降级 | Agent 转用 web_search / 直答 |
| 知识图谱 | kb_search(mode=kg) / kg_query | HASHMM_KG_* | 少了实体关联，其余照常 |
| 全局摘要 | kb_search(mode=global) | 社区未构建即降级 | 宏观问题质量下降，不报错 |
| 语义缓存 | 对上层透明 | HASHMM_SEMCACHE | 只是变慢，结果不变 |

**迁移原则：不做一次性大重构**（大重构 = 新屎山最快的生产方式）。每次触碰旧代码时顺手做三件事：
把散逸调用改走工具面 → 给它补开关 → 给它补"关掉时的降级路径"。三个版本内自然收敛。

## 4. 问题可定位性：三层日志约定

出问题时的排查路径必须是固定的三步，而不是"到处 print"：

1. **哪一步坏了** —— Agent 主干每步产出 trace 事件（已有 HASHMM_AGENT_TRACE），管理后台「运行轨迹」按 会话→步骤→工具 展开；
2. **哪个模块坏了** —— 每个插槽模块用独立 logger 名（`hashmm.skill_packs`、`hashmm.semcache`…），报错必带模块名；`/api/health` 的 components 表（客户端「后端连接」页的健康 chips）给出模块级红绿灯；
3. **为什么坏了** —— 静默降级不等于吞错：`log_suppressed` 全部落日志文件，报障时拉最近日志按 logger 名过滤即可复原现场。

新代码的红线：**禁止裸 `except: pass`**，至少 `log_suppressed(logger, e)`。

## 5. 终局形态与分阶段路线

我们押注的终局（AGI 产品形态的合理收敛点）：
**"一句话（语音）进来 → 意图被准确理解 → Agent 调度全部本地/云端资源 → 高质量完成并交付"** ——
用户不需要知道 RAG、路由、技能包的存在，只体验"说了就做成"。

- **P0（已在 V203 落地）**：工具化主干 + 技能包插槽（SKILL.md 生态兼容，GitHub 直接导入）+
  模型路由面板（成本/质量策略化）+ 模块健康可视化（后端连接页）。
- **P1（下 2-3 个版本）**：RAG 四模块按第 3 节收口；意图理解层从"直接把原话给 Agent"升级为
  "先产出结构化任务卡（目标/约束/验收标准），再交给主干"；语音链路（App STT 已有）接到任务卡。
- **P2**：多 Agent 编排常态化（spawn_worker 从工具升级为调度器：并行、失败重试、结果聚合）；
  技能包支持携带可执行脚本（沙箱内运行，Claude Code 同款模式）；经验回放反哺技能自动生成的闭环打通。
- **P3**：跨端一体（手机说一句，家里电脑上的 Agent 干完活推结果回手机 —— 远程被控 + 接力已铺好底座）；
  按任务难度自动升降模型（路由从"手配"进化为"自学"）。

每个阶段的验收都用同一把尺：**拆掉任何一个模块，系统降级但不倒；加一个模块，只动插槽不动主干。**

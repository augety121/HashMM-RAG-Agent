# P2 训练知识库方案 —— 用 Search-R1 配方训你自己的检索策略模型

> 本文所有数据集与链接均经本轮联网逐一核实，未核实的不写。目的：解决你说的「现在知识库太小、
> 没法做 P2 训练」。结论先行：**P2 分两步走——先用公开多跳 QA 数据集冷启动 / 验证方法，再用
> 你自己的企业语料 + 金标准集做护城河微调。** 前者解决「量」，后者解决「独有价值」。

---

## 一、为什么 P2 必须要大数据，且必须分两步

Search-R1 / R1-Searcher 这类做法是用强化学习（纯结果奖励）让模型自己学会「何时检索、检索什么、
够没够」。它们的实测增益（Search-R1 在 7 个 QA 集上比基线提升约 20–41%）建立在「成千上万条
带标准答案的问题」之上。你现在的企业库太小，直接 RL 会过拟合、学不到稳定策略。

所以正确的工程路径是：第一步先用公开、成规模、带标注的多跳 QA 数据集把「方法链路」跑通、把
检索策略模型冷启动到能用；第二步再把训练 / 评测数据换成你自己的企业语料，让模型在你的真实知识
库上学会多跳——这一步才是大厂用通用语料做不出来的护城河。RAG-Gym 的过程监督结论也提示：只靠
结果奖励容易过拟合训练域，用你自己的数据做域内微调能显著改善泛化。

## 二、第一步：公开多跳 QA 数据集（冷启动 + 方法验证，可直接下载）

这几套是多跳检索领域的标准训练 / 评测集，论文与代码圈普遍使用，全部可公开下载：

HotpotQA 是最常用的多跳 QA 数据集，基于维基百科，约 11.3 万条问答对，关键是它**提供句子级的
支持事实（supporting facts）**，让系统不仅能找到答案还能解释推理，并含一类比较型问题；官方按
难度分为 train-easy 18089、train-medium 56814、train-hard 15661、dev 7405、两个 test 各 7405；
以 CC BY-SA 4.0 许可分发。官网 hotpotqa.github.io，HuggingFace 数据集 hotpotqa/hotpot_qa。

2WikiMultiHopQA（简称 2Wiki）由维基百科 + Wikidata 构建，**提供三元组形式的显式证据路径
（evidence triples）**，可解释性强、能直接评估推理；含比较 / 推理 / 组合 / 桥接-比较四类问题；
共约 19.26 万条，按 167454 训练 / 12576 开发 / 12576 测试划分。原始数据在 2WikiMultihopQA 的
GitHub 仓库。

MuSiQue 专注组合式推理，问题为 2–4 跳，每个问题约 20 个候选段落，每一步依赖上一步的输出，是这
三套里公认最难的，适合用来检验你的多跳回路在真正困难场景下的表现。

Natural Questions（NQ）是 Search-R1 官方示例实际使用的训练集：基于真实谷歌搜索查询 + 标注员
在维基百科上标注的答案，含约 30.7 万训练 / 7830 开发 / 7842 测试。Search-R1 的标准配方就是
「NQ 问题 + 2018 年维基百科 dump 作语料 + E5 作检索器」。

如果想要一个打包好、直接可评测的集合，Salesforce/ContextualBench（HuggingFace）把上面 HotpotQA、
2WikiMultiHopQA、MuSiQue、NQ、TriviaQA 等的 validation 划分聚合在一起，附评测脚本，适合做横向
基线对比。另有 alabnii/morehopqa（HuggingFace），它在 HotpotQA / 2Wiki / MuSiQue 之上再加一层
追问、把答案从抽取式变成生成式，含 1118 条人工验证样本，适合检验更接近真实问答的生成式多跳。

数据规模与许可一句话总结：HotpotQA 11.3 万条、CC BY-SA 4.0；2Wiki 约 19 万条；NQ 约 30 万条；
三者都是公开学术数据集，做研究 / 内部方法验证没有授权障碍（商用前请各自核对许可页）。

## 三、第二步：你自己的企业语料（护城河微调，关键）

公开集只能把方法跑通。真正让你「抢占先机、做到大厂前面」的，是用你自己的数据训练，因为大厂的
通用模型不可能在你的企业知识库上做过多跳优化。具体要准备两样东西：

第一样是企业语料库本身，也就是你产品里已经在用的那些文档（你 HashMM 的知识库导入功能已经支持）。
规模上，冷启动阶段几百到几千篇文档即可起步，越大越好；这部分你本来就有，只是要把它整理成检索器
能索引的统一语料文件（每条一个 chunk，带来源标识）。

第二样是金标准评测 / 训练集，也就是「问题 → 标准答案（最好再加支持段落）」的配对。这是 P2 真正
缺的、也是必须人工 / 半自动构造的部分。好消息是你的项目里已经有大半套生产线：evaluation 目录下
有 casegen.py、eval_set_builder.py、generate_eval_data.py、agent_golden.py、holdout.py 这些能
从语料半自动生成问答对、再人工校验，正好用来在你的企业语料上批量造金标准集。建议先人工精造
200–500 条高质量多跳问题（覆盖你业务里真实会问的跨文档问题）作为种子，再用 casegen 扩充。

## 四、Search-R1 的训练数据格式（照抄即可，已核实）

Search-R1 官方仓库（github.com/PeterGriffinJin/Search-R1）规定每条训练样本是这样一个字典：
data_source 标数据来源；prompt 是一个消息列表，里面 role 为 user、content 为问题文本；
ability 固定写 "fact-reasoning"；reward_model 里 style 写 "rule"、ground_truth 放标准答案；
extra_info 里放 split 和 index。官方给了 scripts/data_process/nq_search.py 作为把原始 QA 转
成这个格式的具体示例，你照着把自己的企业问答对转过去即可。

检索器侧，Search-R1 推荐起一个本地稠密检索服务（search/retrieval_server.py），用 E5 模型
（intfloat/e5-base-v2）+ 你自己的语料索引（faiss 的 e5_Flat.index + 语料 jsonl）；它同时支持
BM25 稀疏检索、稠密检索，以及 Google / Bing 等在线搜索引擎，检索服务与 RL 训练管线分开起。
也就是说，你可以把检索服务直接指向你 HashMM 已有的检索后端，让训练时的「搜索工具」就是你的
生产检索器——训出来的策略天然贴合你的线上系统。

参考实现除官方仓库外，还有 Xinyi-0724/Search-R1-Qwen3（更新框架兼容性、含 NQ + E5 + 维基的
完整训练走通指南）和 RUCAIBox/R1-Searcher（两阶段、纯结果奖励、不需要冷启动蒸馏），都可作为
你落地时的对照实现。

## 五、训练配方要点（来自已核实论文，供真机执行时参照）

模型规模选 3B–7B（Search-R1 在 Qwen2.5-3B / 7B、Llama3.2-3B 上都验证过，7B 增益最大）。
奖励用纯结果奖励（答案对不对，rule-based），不必一开始就上复杂的过程奖励——这正是 Search-R1
证明有效的极简设计。训练算法 PPO 或 GRPO 均可（官方两者都支持）。一个关键稳定性技巧是
retrieved token masking：把检索回来的内容 token 在计算损失时屏蔽掉，只对模型自己生成的推理 /
查询 token 算梯度，否则训练会不稳。交互协议沿用 Search-R1 的标签体系：<think> 包推理、
<search> 触发检索、<information> 包检索结果、<answer> 给最终答案。

资源上这一步需要 GPU（沙箱里跑不了，需在你的真机 / 服务器执行）。建议先在公开集（如 NQ 或
HotpotQA 的一个子集）上把整条 RL 管线跑通、确认 reward 在涨，再切换到你的企业金标准集做正式
训练。等结果奖励版稳定后，再考虑按 RAG-Gym 的思路升级到过程监督（对每一步检索决策打分），
它在域外集上相对结果监督有 3.2%–11.6% 的 F1 提升，泛化更好——你的 judge_calibration.py 已经
是这套过程奖励的零件。

## 六、和你已落地的 P0 怎么衔接

你现在（V103.53）已经有了免训练版的检索回路 + 不确定性闸，这就是 P2 训出来的模型未来要替换 /
增强的那个「停止与续检策略」。P0 的回路用的是 LLM 文本判停 + confidence.py 量化闸；P2 的目标
是把这个「判停 / 续检 / 子查询生成」的策略，从规则 + 通用 LLM，升级成一个在你企业语料上专门
训练过的小模型。换句话说，P0 是骨架与兜底，P2 是给这副骨架装上一颗在你数据上长出来的大脑。
接口上无需重构：训练出的策略模型只要实现 AgenticRetriever 已经定义好的 llm_fn（给定证据摘要
返回 search/finish 决策）即可平滑替换。

## 七、下一步建议

最务实的顺序是：你先在真机上用 NQ 或 HotpotQA 子集把 Search-R1 这条 RL 管线跑通、把检索服务
指向你自己的检索后端，确认 reward 上升；同时用项目里的 casegen / eval_set_builder 在你的企业
语料上人工精造 200–500 条多跳金标准题。这两件事就绪后，把训练数据换成你的企业集正式训练，
产出第一版「你专属的检索策略模型」。我可以下一步帮你把项目里的 casegen / eval_set_builder
接出来、写一个「企业语料 → Search-R1 训练格式（含 reward_model 字段）」的转换脚本，让你拿到
金标准题后一键导出成可训练的数据文件。

## 一、现状诊断（基于实测）

### 1.1 你已经造好的，比你以为的多
- 后端 **6.3 万行 Python**，19 个子模块；客户端 Electron **1.3 万行 JS**，前端 Next.js **1.65 万行 TS**（77 个组件），安装器 1177 行 C++。
- 智能层 `hashmm/agent/`（7307 行 / 36 文件）已有：ReAct 工具循环 `loop.py`（1989 行）、子智能体编排 `orchestrator.py` + `subagents.py`、上下文工程三件套 `context_manager.py` / `context_pack.py` / `conv_compact.py`、纠错式 RAG `crag.py`、生成-评判精炼 `evaluator_optimizer.py`、置信度校准 `confidence.py`、经验负规则 `exp_rules.py`。
- 评估框架 `hashmm/evaluation/`（3355 行 / 15 文件）已有：质量门 `gate.py`、金标准集 `agent_golden.py`、指标 `metrics.py`（recall / mrr / ndcg / grounding）、回归对比、judge 校准。
- 客户端 Electron 层较成熟：自动更新（autoUpdater）、崩溃上报、单实例锁、`contextBridge` 隔离、computeruse、远程配对、OCR 都有。

**这说明你不缺能力，缺的是把能力「用对地方」。**

### 1.2 核心问题：造好的智能，没接进用户实际走的路径
实测客户端主聊天路径 = `/api/conversations/{id}/stream`（`frontend-next/lib/api.ts:481`）→ `generate_sse_async`（`hashmm/api/streaming.py`）。

这条**活路径**实际只用了：`loop`（ReAct）+ `orchestrator`（子智能体）+ `conv_compact`（基础压缩）+ `confidence`（且被开关关着）。

它**完全没用**：`CRAG`、`evaluator_optimizer`、`context_manager`（高级长程上下文）、`context_pack`（相关性装箱）、`subagents`。

这些高级模块在 `run_agentic_chat`（`/api/chat/agentic`，`server.py:551`）里——一个**客户端根本不调用**的旁路端点。

> **结论**：你造的最强答案质量机制（纠错检索、生成-评判、相关性装箱、高级上下文压缩），用户在主界面里拿不到。这是「两条并行路径」的架构债。

### 1.3 大量能力被环境开关默认关着（实测默认值）
`HASHMM_CONFIDENCE=0`、`HASHMM_USER_MEMORY=0`、`HASHMM_AGENTIC_RETRIEVAL=0`、`HASHMM_LLM_ROUTING=0`、`HASHMM_PARALLEL_TOOLS=0`、`HASHMM_SCHEDULER=0`、`HASHMM_EXP_RULES` 无默认（=关）、`HASHMM_KG_RETRIEVAL` 关。

> **结论**：你的 agent 在生产里跑的是「基础档」，高级档造好了锁着。

### 1.4 知识图谱：0 社区
生产 KG：983 实体 / 303 关系 / **0 社区**。社区检测从没成功跑过 → global / 社区级检索能力实际是空的。

### 1.5 评估框架很全，但大概率没在跑
`gate.py` / `agent_golden` / `metrics` / 回归对比都有，但 `ci/backend-ci.yml` 只有 955 字节。

> **结论**：你有「能说不的验证者」的全部零件，但没把它变成每次改动的守门人。橙皮书说「最难也最值钱」的那一环，没真正立起来。

### 1.6 客户端工程化短板（实测）
- **前端**：懒加载 / 代码分割 **0 处**（`Suspense` / `lazy` 全无）→ 1.65 万行全量加载，冷启动慢、首包大；`ErrorBoundary` 仅 **2 个**组件 → 某个面板崩了可能白屏拖垮整个界面；无障碍 `aria` 仅 **1 个** → 达不到大厂可访问性基线。
- **Electron**：相对成熟，是较小的短板。

## 二、核心判断：下一个工程是什么

你问「loop 工程之后是什么」。基于上面的现状——你能力已经够多了——**真正的下一个工程不是再造新能力，而是：**

> ## 「评估驱动的上下文工程」（Evaluation-Driven Context Engineering）
> 把已经造好、但休眠 / 旁路 / 关着的智能，**在评估护栏下逐个接进用户的活路径、默认打开、并用数据证明它确实更好**。

**为什么是这个（这才是对标大厂的方式）：**
1. 大厂不靠「功能堆叠」，靠**可度量的改进**——每个能力上线前用 eval 证明有正收益、不引入回归。你的 `gate.py` 就是干这个的，但没用起来。
2. Agent 变聪明的真正杠杆是**上下文工程**：模型每一步看到什么，决定它多聪明。你的 `context_manager` / `context_pack` 造好了却没接主路径——这正是**最大的单点收益**。
3. 把「两条路径」合并成一条**评估过的最优路径**，既让用户拿到最强能力，又消掉架构债。

**一句话**：从「能力堆叠的 loop 工程」→「评估驱动、上下文为核心、单一最优路径的 **智能工程**」。

## 三、后端路线：把已造好的智能，评估驱动地接进主路径

每个阶段都配「依据（你的哪个文件）+ 怎么用你的 eval 框架验收」。

### 阶段 A — 立起验证者（地基，必须先做）
- 把 `evaluation/gate.py` 接进 CI（扩展 `ci/backend-ci.yml`）：每次改动跑金标准集（`agent_golden`），算 recall / mrr / ndcg / grounding，**有回归就挡住合并**。
- 用 `eval_set_builder` / `casegen` 生成一个覆盖你知识库真实问题的固定金标准问答集。
- 产出：一条命令、一张分数表、回归就红。**之后所有「激活」都用它验收。**
- **为什么先做**：没有这个，后面每打开一个开关都是凭感觉，会重蹈幻觉覆辙。这一步是整套方案「不靠感觉、对标大厂」的根本。

### 阶段 B — 统一答案质量到主路径（最大的用户可感收益）
把休眠的质量模块按「**先证明、再默认开**」接进 `generate_sse_async`：
1. **`context_pack` 相关性装箱**（已造，主路径没用）：相关性高的检索结果多给上下文预算，替代粗暴拼接 → A/B 看 grounding 升了就默认开。
2. **`CRAG` 纠错检索**（`crag.py`，主路径 0 引用）：检索弱时重写 query 再检索。它本身就设计成「只在明显弱时触发」，不会拖累好答案 → eval 证明 recall 升、无回归 → 默认开。
3. **`evaluator_optimizer` 答案精炼**（主路径 0 引用）：答案对不上来源时带反馈重生成 + 强制引用。延迟换质量，可只在高价值 / 低置信时触发。
4. **`confidence` 默认开**（已接但 `HASHMM_CONFIDENCE=0`）：低置信时显式 hedge、不硬编——这是你想要的「诚实」落地的硬支撑。

### 阶段 C — 上下文工程升级（让长对话 / 长任务变聪明）
- 接上 `context_manager`（高级长程压缩，主路径 0 引用），替换 `history[-6:]` 式截断 → 长对话不再「聊久了失忆」。
- 统一**上下文预算分配**：系统提示 + 检索 + 记忆 + 技能 + 历史，按预算和相关性统一装箱，而不是各塞各的。
- 用多轮、需记住开场需求的金标准任务验收。

### 阶段 D — 把「越用越聪明」接通并默认开（评估护航）
- `USER_MEMORY`（默认关）、`exp_rules`（经验负规则，默认关）、skill 注入：eval 证明不引入回归后默认开。
- KG：先跑通**社区检测**（把 0 社区补上），global 检索才有意义；再定 `KG_RETRIEVAL` 默认策略。
- 这一步把你前几版做的 loop 面板（自我进化 / 记忆 / 发现 / 调度）从「能看能点」变成「默认在后台真起作用」。

## 四、客户端路线：对标大厂工程化

### 前端（Next.js）— 补足生产基线
1. **代码分割 / 懒加载**（现 0 处）：19 个 desktop 面板 + 15 个 admin 面板用 `React.lazy` + `Suspense` 按需加载 → 冷启动只加载首屏、首包大幅减小。**这是大厂前端的硬基线，你现在完全没有。**
2. **错误边界**（现 2 个）：每个面板包一层 `ErrorBoundary` → 单面板崩溃只显示局部错误卡，不白屏拖垮全局。
3. **加载 / 空 / 错 三态**：每个数据面板统一 skeleton、空状态、错误重试 → 你的面板现在很多是「读取中…」裸文本。
4. **无障碍**（现 1 个）：关键交互补 `aria-label` / `role` / 键盘可达 → 达到大厂可访问性基线。
5. **设计系统统一**：抽出统一 token / 组件（按钮 / 卡片 / 输入），减少各面板各写一套的不一致。

### Electron — 锦上添花（已较成熟）
1. 崩溃恢复 + 会话恢复：崩了能自动重启并恢复上次对话。
2. 离线优雅降级：后端没起来时 UI 明确告知 + 可重连，而不是各种失败。
3. 内存看护：长跑不泄漏（你已有 `test_storage` / `test_workspace`，补内存基线测试）。
4. 遥测打通：崩溃 / 性能 / 关键错误（可选、隐私友好）汇到一处——大厂靠这个发现问题。

### 架构债清理
- 合并「两条路径」：让 `/api/chat/agentic` 的最优逻辑并入主 `generate_sse_async`，或废弃旁路端点，避免两套代码长期分叉。

## 五、分阶段优先级（我的建议）

| 优先级 | 内容 | 为什么 |
|---|---|---|
| **P0**（地基） | 阶段 A 立验证者 + 前端代码分割 / 错误边界 | 没验证者后面都凭感觉；冷启动 + 不白屏是用户最先感知的 |
| **P1**（最大智能收益） | 阶段 B 答案质量统一到主路径 + confidence 默认开 | 把造好的最强能力交到用户手里，且有数据背书 |
| **P2**（深度） | 阶段 C 上下文工程 + KG 补社区 | 长对话变聪明 + 补上空缺的图谱能力 |
| **P3**（长期复利） | 阶段 D 越用越聪明默认开 + 客户端三态 / 无障碍 / 遥测 + 架构债清理 | 复利型改进，让产品长期自我进化 |

> **铁律**：每个阶段的验收都过阶段 A 的 eval 门——**没有分数提升或引入了回归，就不合并。** 这是整套方案防幻觉、对标大厂的根本保证。

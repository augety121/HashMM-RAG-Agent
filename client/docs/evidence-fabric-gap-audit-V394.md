# HashMM Evidence Fabric 实现审计（V394）

审计日期：2026-07-23

这份文档只记录能够由当前仓库代码和测试证明的状态。目标数值、产品设想和外部产品能力不会被写成 HashMM 已经实现的事实。

## 结论

HashMM 已经具备 Evidence-Native Work Agent 的核心协议骨架，但附件中的路线尚未全部完成。当前最准确的描述是：

- 工作运行、证据图、完成门、上下文压缩、浏览器—画布证据关联、多 Agent 生命周期与技能版本治理已经进入真实主链；
- 三个图平面的原子 generation、按证据变化进行完整因果失效传播、自适应 Agent 拓扑收益规划、全工具补偿目录以及跨设备混沌验证仍需继续；
- V394 完成了此前最明确的发布缺口：技能候选必须通过同源历史成对回放、固定安全对抗、质量/成本/延迟门禁，之后才允许人工发布。

## V394 发布门

生产技能的状态转换现在是：

```text
成功经验
  -> 隔离候选
  -> 静态安全与权限差异门
  -> 同一模型上的基线/候选历史成对回放
  -> 固定秘密泄露与审批绕过对抗样本
  -> 质量、单例退化、Token、延迟、完整性门
  -> 人工确认
  -> 基线哈希 CAS 发布
  -> 可精确回滚
```

关键边界：

- 生产接口只从服务端选择当前账号拥有的反馈案例，客户端不能提交“有利样本”绕过发布门；
- 显式来源 ID 只能调整同一 owner 数据的优先级，不能跨账号选取；
- 评测表只持久化案例、输入、参考答案和生成答案的 SHA-256，以及分数、Token、延迟和状态，不复制私有对话正文；
- 模型调用前后都校验生产基线，回放期间发生编辑会令评测失效；
- 少于 2 条相关历史案例时结果为 `insufficient_evidence`，不能发布；
- 通过自动门禁仍不代表自动上线，最终必须由用户明确采用；
- 私有回放集只能发现已覆盖任务上的退化，不能证明候选在所有真实任务上更优。

## 桌面端与 App

本轮桌面端已接入候选评测和发布阻断解释，包括历史/对抗案例数、基线/候选质量、Token、延迟与逐门状态。

App 不在当前仓库的可写实现范围内，因此本轮没有声称修改 App。Work Runtime 仍是桌面端和 App 应共同消费的权威状态；后续 App 应把评测事件投影为行动收件箱中的“待评测 / 证据不足 / 待批准 / 已阻断”，不应复制桌面评测控制台。

## 指标声明

附件中的以下数值仍然是验收目标，不是已经达成的宣传结论：

- 1000 次跨设备指令重复外部副作用为 0；
- 来源变化后的过期主张漏检率低于 1%；
- DOM 小幅变化后的证据重定位成功率高于 90%；
- 长对话压缩后关键约束保持率高于 98%；
- 多 Agent 的成本调整后成功率显著高于单 Agent。

V394 能确定证明的是技能发布门的功能与失败分支，而不是整个产品已经超过 Codex 或 Claude Code。

## 后续优先顺序

1. 为 Knowledge / Work / Evidence 三平面建立原子 generation 和 active-generation 切换。
2. 建立 Adaptive Agent Mesh 的单 Agent 对照组、拓扑效用记录和独立验证盲评。
3. 形成全工具补偿目录，并把不可撤销范围写入执行前审批和执行后收据。
4. 建立 Browser Evidence DOM 扰动重定位数据集，持续统计而非主观宣称成功率。
5. 对桌面端—App Work Runtime 做断网、乱序、重复事件和旧缓存覆盖的收敛测试。

# HashMM V1500 交付说明

## 结论

V1500 已完成代码实现、回归验证和三类交付物构建。本轮解决的是生产身份不一致、多用户任务被物理桌面锁串行化、客户端过度轮询、本地会话正文缺少账号隔离加密，以及安装器版本和交互细节不一致。实现契约见 `docs/HASHMM_V1500_MULTI_USER_RUNTIME_SPEC.md`。

## 已实现

- 生产 Supabase 身份配置改为环境权威；新增不泄露密钥的 `/api/auth/identity-contract`，桌面登录可准确识别 Supabase 项目不一致并携带 request id。
- AgentLoop 使用全局/账号双层并发准入；默认全局 12、单账号 3。普通 Agent、RAG、文件和自动任务不再占用 Browser/Computer Use 的物理设备锁。
- 桌面 dispatch 与前端网络访问增加有界 deadline、GET 条件重试和抖动；写请求不因超时自动重放副作用。
- 桌面同步调整为前台 30 秒、后台 5 分钟，联网和重新可见立即对账；Android 远程配置改为登录强刷与 6 小时 TTL。
- Android 本地副本使用 Android Keystore AES-256-GCM、账号/文件 AAD、`noBackupFilesDir`、原子替换和旧缓存一次性迁移。
- 桌面完整会话正文改为 Electron `safeStorage` 加密的账号独立副本；Renderer 只保留侧栏元数据，账号切换不再互删缓存。
- 原生安装器扩大窗口控制按钮和主要操作热区，补齐可访问名称、Escape 行为与首次安装协议显式勾选；版本资源统一为 6.0.0。
- 当前私有 `.env` 已加入生产身份提供方和多用户并发配置；服务器 ZIP 不包含该文件或任何真实凭证。

## 部署与诚实边界

- 服务器当前在线实例此前仍是 V1302；上传 V1500 ZIP、保留服务器私有 `.env`、执行 doctor 并重启后，线上才会成为 V1500。不能把本地构建写成已部署。
- Windows EXE 的 SHA-256 完整性已验证，但当前 Authenticode 状态为 `NotSigned`；正式公开分发仍需代码签名证书。
- V1500 的跨端低延迟基线是自适应轮询与恢复触发，不是完整 Supabase Realtime Broadcast。
- Desktop 的完整消息正文和 refresh token 已加密；短期 access token 与非敏感侧栏元数据仍在 Renderer 存储中，不能表述为“全部本地数据均已加密”。
- 真实双账号并发、校园网/5G、断网恢复与 24 小时稳定性仍需在实际部署环境验收；自动化测试不能替代现场网络和设备证据。

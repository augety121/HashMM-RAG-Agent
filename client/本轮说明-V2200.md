# HashMM V2200 · Direct-First Remote Fabric

## 结论

远程不应“完全不经过服务器”，也不应让屏幕数据默认经过 HashMM API。V2200 将两类流量分开：

1. 控制面：账号鉴权、设备发现、权限审批、会话审计和 WebRTC 信令经过 `https://hashmm.hashlens.org`。
2. 媒体面：屏幕、音频与 WebRTC DataChannel 优先端到端直连；直接候选失败时使用自有 TURN；两者均未建立才启用低帧率 HTTPS/JPEG 应急画面。

该边界与 RustDesk 的 rendezvous/direct/relay 分工、Sunshine/Moonlight 的端侧采集编码以及标准 ICE/TURN 模型一致。UU 远程未公开足够的内部协议细节，因此本轮不根据宣传材料臆测其私有实现。

## 已完成

- Electron 主进程持久 host supervisor，固定 `ws` 实现并解析真实 `MessageEvent`。
- 隐藏媒体窗口与主机租约解耦；采集窗口关闭只恢复媒体，不再让电脑从 App 设备目录消失。
- host 认证帧发送状态、关闭码、关闭原因、attempt id 和 35 秒入站 watchdog。
- 已消费 viewer ticket 的诊断保留与 viewer lease 真值。
- `transportPolicy=ice-direct-turn-fallback`、`transportMode=auto|turn-only` 和 12 秒 legacy grace。
- 桌面查看端、桌面主机和 Android 的 direct-first 行为一致。
- Android TURN-only 与旧 HTTPS 帧轮询语义拆分；WebRTC 恢复后立即停止旧帧轮询。

## 部署要求

- 公网入口必须为 HTTPS/WSS，当前为 `https://hashmm.hashlens.org`。
- 复杂 NAT 的生产可用性依赖自有 coturn：配置 `HASHMM_TURN_URLS` 和至少 32 字节的 `HASHMM_TURN_SHARED_SECRET`；服务器和客户端时间必须同步。
- Cloudflare Tunnel 只承载 API/WSS 控制面，不应用来代理 UDP 媒体；TURN 应有可达的 UDP/TCP/TLS 端口和独立容量监控。
- 需要多后端实例时，先实现共享 presence/broker 和跨实例信令路由；仅增加 API 副本会造成同账号设备落在不同进程后互相不可见。

## 验收矩阵

- 已自动验证：Python 远程会话/设备/transport 测试；真实本机 WebSocket host 注册；桌面 Node 合约；前端测试与类型检查；Android unit test。
- 发布前必须实测：同局域网 host 候选、手机流量↔校园网 srflx 候选、对称 NAT relay 候选、TURN 禁用后的 legacy HTTPS、断网 3 秒恢复、桌面采集窗崩溃恢复、账号 token 刷新、连续 24 小时租约。
- 验收证据必须记录选中候选类型、协议、RTT、断线原因与匿名 attempt id；不得记录 token、SDP、ICE 地址或屏幕内容。

# HashMM V1600 交付说明

本轮处理的根因不是 Supabase 容量不足，也不是 Cloudflare Tunnel 断线。旧版在会话 GET 中同步拉取并回写 Supabase，Realtime 又触发 App 再次 GET；同步 `urllib` 与远程 token 校验还运行在 asyncio 事件循环中。因此一个客户端的同步会拖慢 `/api/health`、其他账号和桌面端请求，并被客户端误报成全局掉线。

V1600 将后端设为对话唯一权威源，移除读侧写入和 App 直读回退；旧数据云恢复改为显式操作。App 增加登录生命周期绑定、同步 single-flight、Realtime 合并、共享连接池、本设备退出和消息待投递；桌面端增加连接状态迟滞。Supabase 镜像写入改为固定 worker、有界容量和实体级合并，兼容网络调用全部从高频请求事件循环隔离。

## 部署顺序

1. 在 Supabase SQL Editor 运行 `sql/20260810_v1600_cross_device_kernel.sql`。迁移可重复执行，但正式环境仍应先备份并记录执行回执。
2. 上传最终 V1600 server 包并保留服务器私有 `.env`，先运行 `./start-hashmm1.sh doctor`，再启动服务。
3. 验证 `https://hashmm.hashlens.org/api/livez`、`/api/readyz`、`/api/health`，并确认 Supabase 项目、JWT issuer 与客户端使用的是同一身份域。
4. 安装 Desktop 7.0.0 和 App 4.0.0。旧客户端不得作为 V1600 跨端验收依据。
5. 使用两个普通账号、同账号双设备、弱网恢复、单端退出四组场景验收；单端退出不得让另一端掉线，任一账号的慢请求不得阻塞其他账号。

## 诚实边界

- 本轮实现的是以本地 SQLite 权威数据为耐久来源、Supabase 镜像队列有界合并的同步模型；镜像 worker 本身不是独立的持久化消息队列。进程重启后由权威数据和显式恢复路径重新对账，不宣称“所有尚未发送的镜像任务逐条续跑”。
- Cloudflare Tunnel 公网健康检查此前已经返回 200；本轮没有替用户执行 Supabase 生产迁移、真机外网 soak、双账号长时间压测或发布证书签名，因此这些仍是部署验收项。

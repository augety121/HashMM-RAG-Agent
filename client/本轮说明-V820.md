# HashMM V820 本轮说明

## 目标与结论

V820 按 `docs/API_PLATFORM_V820_SPEC.md` 完成了一次 API 平台大版本迭代。重点不是继续增加接口数量，而是把 V810 的 Responses、Chat、Threads、Runs、RAG 和 Usage 串进同一条可运营访问链：每个用户可创建独立 Key，每个 Key 有自己的权限与资源边界，调用前经过原子限流/并发/配额准入，调用后按 Key 结算和审计，撤销后新请求立即失效。

本轮没有改变服务器或桌面 Python 的 pip 依赖集合。

## 已实现

1. **持久化 API Key 生命周期**：新增 owner-scoped Key 创建、列表、详情、revision 更新、禁用/启用、不可逆撤销和用量接口。完整密钥至少含 256 bit 随机量，只在创建响应显示一次；服务端只保存 SHA-256 摘要与可展示前缀。
2. **统一鉴权上下文**：`/v1` 支持 managed key、旧 `HASHMM_API_KEY`、管理员会话与显式开发 open 模式。查询参数密钥被拒绝；直接来源 IP、状态、过期、Scope、模型 allowlist 和项目 allowlist 在执行前校验。
3. **原子治理状态机**：Key 级固定分钟 RPM、TTL 并发租约和幂等费用配额预占/结算均持久化。SQLite 事务与条件更新保证并发请求不超卖；异常、客户端失败或执行错误释放 Key 预占、并发租约和 owner 预算。
4. **Key 级用量归属**：`usage_events` 以加法迁移增加 `access_key_id`；历史/legacy 事件继续参加 owner 汇总。Responses、Chat Completions 与 legacy RAG 均记录实际服务可得的 Token 估算与成本来源，估算值不冒充供应商正式账单。
5. **Chat 与 Responses 终态一致**：Chat Completions 改用与 Responses 相同的原子完成函数，响应 `completed` 与 `response.completed` 可重放事件在同一事务提交。
6. **自助控制台**：设置新增“API 访问”页，提供最小 Scope、模型/项目/IP、RPM、并发、费用配额、过期、一次性复制、revision 冲突刷新、30 天 Key 用量和二次确认撤销。完整 secret 不写入 localStorage、sessionStorage、URL 或审计日志。
7. **发布包闭环**：服务器包的必需能力清单新增 `platform_access.py`、`platform_keys.py` 与 V820 Spec；ZIP 继续排除用户数据、密钥、模型、缓存、测试、桌面与旧归档。

## 真实边界

- V820 是单实例/共享 SQLite 的可运营访问平面，不是 Redis 多活全局限流。多节点线性一致限流属于 V830+。
- 尚未实现 sub2api 的多供应商账号池、账号粘性调度、上游账号健康/封禁与成本路由；HashMM 当前模型管理器不能被描述成代理账号池。
- 尚未接入 Stripe、Cloudflare Wallet、x402 或任何真实资金收付、退款和对账。Key 的 `quota_limit` 是本地调用准入与计量约束，不是钱包余额。
- Key 成本目前以现有价格表和确定性 Token 估算为主；只有供应商真实返回的成本才进入 provider-reported 字段。
- 本轮没有蒸馏、保存或展示 Codex/模型隐藏思维链；项目只保存公开任务链、检查点、审批、工具回执、产物与验证证据。

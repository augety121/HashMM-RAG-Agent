# HashMM V371 本轮说明

## 本轮目标

把 V370 的任务证据图继续推进为可执行但不越权的任务前沿：系统不仅说明“哪里被阻塞”，还要根据真实任务图、工具注册表、已持久化执行范围和联网策略，确定最小的下一工作集、候选能力、作用域缺口、联网缺口与安全降级路径。该机制服务于 Chat、长任务、多 Agent、桌面端和 App，同一事实只由服务端协议表达，不由各端伪造演示状态。

## Graph-guided Execution Frontier

- 新增 `hashmm.execution-frontier.v1`。每个未解决阻塞项包含期望状态、已观察状态、阻塞节点与一跳工作集、候选工具、执行范围、联网要求、首选路径、降级路径和最小下一动作。
- 路由只读取任务证据图、真实工具注册表和已持久化权限数据；不会执行工具、不会替用户确认、不会自动扩大文件、网络、会话或 Agent 范围。
- 检索任务优先选择本地证据能力 `kb_search`、`kg_query`，本地证据不足时才把 `web_search` 列为需要联网的候选路径；联网不可用时保留安全降级路径和明确缺口。
- Artifact、失败工具、失败 Agent 与未通过检查分别映射到文档/文件生成、重试或诊断、受控 worker、独立复核路径。路由缺失或状态不一致会计入完整性违规，不以模型文本补造能力。
- 每次重建都会与上一前沿核对；阻塞消失时写入 `converged`，仍未满足时只保留当前未解决工作集，避免长任务反复执行已完成步骤。

## Chat、长任务与多 Agent 串联

- 普通 Chat 的运行清单持久化执行前沿；下一轮仅通过显式“不可信运行数据”边界读取前沿摘要，不允许前沿覆盖用户新指令。
- 持久化长任务每轮根据真实 attempt、工具结果、Artifact 和检查结果重建任务图与执行前沿；恢复旧任务只重建元数据，不重放工具。
- 长任务的图反馈优先使用“已就绪”的最小下一动作；仅有缺权、缺联网或需用户输入的路径不会伪装成可执行。
- 多 Agent 团队状态使用同一协议呈现共享来源、角色失败、缺少交付物、验收检查和下一工作集。子 Agent 仍继承更窄的用户、会话、工具和联网边界。
- 运行清单 handoff 的 `next_action` 与执行前沿对齐，使短对话继续、后台长任务和移动端接力使用同一可验证事实。

## 桌面端与 App

- 桌面端统一上下文的“证据/运行”页展示未解决项、已就绪项、作用域限制、候选路径和最小下一动作；“继续”只把动作放回当前 Chat 输入框，不直接执行或授权。
- 桌面端长任务详情展示下一工作集和范围限制；质量看板新增前沿覆盖、可行动、已收敛、缺范围、等待输入、路由覆盖与完整性违规。
- App 的对话完成卡、长任务、多 Agent、总控中枢和质量页解析同一服务端执行前沿。服务端没有前沿时不生成演示数据，也不在手机端获取桌面本地文件、Browser Use 或 Computer Use 的额外权限。
- App 质量页会把作用域受限与前沿完整性异常显示为需要复核的工程状态，不将“有路由”解释成任务已正确完成。

## 严格边界

- 执行前沿是确定性编排与可观察协议，不是访问控制器、批准器，也不是答案正确性的证明。
- `ready` 只表示候选能力满足当前已持久化范围；是否执行仍由 Agent loop、工具敏感级别、用户确认和审计策略共同决定。
- 路由覆盖率、图密度和前沿数量都不能替代来源质量、独立复核、真实 Artifact 或运行结果。
- 外部网站登录态、真实 Browser/Computer Use 行为、生产 Supabase 数据和远程 MCP 仍需在对应生产环境单独验收；本轮本地验证不冒充生产证据。

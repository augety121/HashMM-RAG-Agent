# HashMM V348 本轮说明

日期：2026-07-19

## 本轮完成

- 把高风险工具批准从页面内按钮提升为可恢复协议 `hashmm.tool-approval.v1`。请求绑定真实用户、会话、assistant message、工具名、参数指纹、工作目录、风险等级和过期时间；刷新、重开会话或切换桌面端/App 后仍可继续处理。
- 工具批准采用严格状态机：`pending -> approved/declined -> consumed`。批准只对完全一致的工具名、参数和会话生效，并在一次成功校验后消费；参数被修改、请求过期、重复使用或跨账号访问都会拒绝。
- 新增属主校验的批准接口。不存在和无权访问统一返回 404；接口只记录决定，不直接执行工具。批准后由原 Chat 发起正常继续轮次，重新经过 AgentLoop、权限、Hook、工具执行和审计链。
- Desktop Chat 与 App 首页/详情 Chat 使用同一条持久消息渲染批准卡，显示经过服务端裁剪和脱敏的参数；支持拒绝、批准并继续以及换设备后继续。App 动态页把该状态标为“等待工具批准”并回到原 Chat 接管。
- 修复一个真实的执行顺序缺陷：并行预取过去可能发生在权限和 pre-tool Hook 之前。V348 仅允许已登记的只读本地检索工具预取；联网工具不预取，存在 pre-tool Hook 时完全停用预取，因此副作用工具不可能借预取绕过批准、Hook 或审计。
- Supabase 继续通过属主隔离的 messages/client_activity 同步跨端待办；精确批准凭据只保存在服务端 SQLite，不把可执行原始参数暴露给客户端或云端活动表。
- 对标依据只采用可核验机制：本地 `codex-main` 的批准请求/决定协议、本地 `openai-agents-python-main` 的 Human-in-the-loop 中断与可序列化 RunState，以及用户四份资料中的耐久状态、负向工具用例、权限分层、轨迹评测和停止条件。未把资料中的未来产品描述当作已实现事实。

## 部署与限制

- 服务器、桌面端和 App 应一起升级。旧客户端能读取暂停文本，但不会呈现结构化批准卡；批准凭据不会为了兼容旧客户端而降级成普通用户文本。
- V348 有意只提供“批准这一次”，没有“永久允许”或“本会话全部允许”。这是最小权限设计，不是功能缺失；后续若增加会话级批准，必须绑定工具、参数范围、工作目录、有效期并可撤销。
- 点击批准不会在 HTTP 决定接口中直接执行副作用。Desktop/App 会提交一个正常继续轮次，服务端再次匹配并一次性消费批准；因此离线批准会保留为待继续，而不会在用户不可见时偷偷执行。
- 本轮通过了原生安装器的发布源门禁，但没有运行 `installer-native/build-all.bat` 重新生成正式 EXE。正式 Windows 发布仍须使用该唯一流水线，并核对 EXE、`.sha256` 和 `.release.json` 三者一致。

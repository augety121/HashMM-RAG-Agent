# 本轮说明 · V339（2026-07-17）—— 共享浏览器正式接入 Agent 主框架

本轮先做了“已写功能是否真的被产品使用”的接线审计。确认此前存在两个分裂实现：Python 后端的
`browser_kernel` 在桌面内置运行时没有 Playwright 时会降级为文本读取；Electron 的
`browser-use.js` 虽能真实点击、输入和截图，却主要只被派活 runner 使用。已有
`browser-cockpit.html` 没有安全加载入口、没有进入安装清单，主前端也没有消费它的事件，因此它在
发布产品里实际上不可达。

V339 把这条链收成一个可验证闭环。HashMM 后端迭代号为 **V339**，桌面端、MCP client/server
身份版本与原生安装器版本为 **1.12.0**。MCP wire protocol 仍保持项目实际支持的
`2024-11-05`，没有把产品版本误写成协议版本。

## 已完成

### 1. 浏览器成为桌面主框架的一等入口

- 主侧栏新增“共享浏览器”，普通桌面用户可直接进入，不再藏在管理员“高级能力”的 JSON 派活页。
- 用户以自然语言填写浏览/调研或网站验收任务；前端把当前 `conv_id`、目标和证据 schema 投递给
  `desktop` runner，后者复用现有 AgentLoop 与真实 Electron Browser Use，结果回到明确的当前对话。
- 页面展示最近浏览器任务的 pending/claimed/done/failed 状态和真实结果，不再要求用户手写
  `browser_use` payload。
- 快捷键 `Ctrl+Shift+B` 和 UI 按钮都能打开共享浏览器；窗口与主 UI 消费同一事件源。

### 2. 原孤立 cockpit 变成安全的实时共享视图

- 新增 `browser-preload.js` 窄桥，只暴露状态、清轨迹、显示受控页和事件订阅；窗口保持
  `nodeIntegration:false`、`contextIsolation:true`、`sandbox:true`，没有 raw IPC、文件或 shell 能力。
- `browser-cockpit.html` 不再依赖 `window.require`，也不再在 Electron 中播放脚本演示；它会回放主进程
  保留的真实动作，实时显示 webContents 截图、可交互元素编号、URL、滚动位置和成功/拦截状态。
- `browser-cockpit.html` 与 `browser-preload.js` 已显式加入 electron-builder 清单，发布门禁会验证它们
  确实进入 app.asar。
- 主框架内也显示最近真实截图，所以浏览器不是只能在独立窗口中看到。

### 3. 站点级权限和跨站边界

- 首次访问每个 host 都由原生对话框询问“仅本次任务允许 / 始终允许 / 阻止”；持久策略原子写入
  `userData/browser-policy.json`，界面可以查看和撤销。
- `browser:*` 统一归为敏感 IPC；只有可信 app 文件或受信壳层 origin 能读取浏览历史、修改策略或打开
  浏览器窗口。
- 仅允许无内嵌用户名/密码的 HTTP(S) URL；云主机元数据 IP 硬阻止。本机 localhost 仍可在明确授权后
  用于预览开发中的应用。
- page-initiated 跨站导航、重定向和弹窗不会静默越过授权边界：先阻止并把目标 URL 回给 Agent，Agent
  只能显式 `navigate`，随后触发用户授权。
- 浏览器保持独立持久 profile `persist:browser-use`，不自动共享用户日常浏览器标签或会话。

### 4. 敏感动作二次确认与不可信页面隔离

- Browser Use 继续只暴露编号化的 navigate/read/click/type/scroll/wait 等窄动作，不提供自动文件上传。
- 输入密码、验证码、银行卡/CVV、API key/secret 等敏感字段前强制确认；点击付款、购买、下单、删除、
  注销、发送、发布、授权等疑似外部副作用控件前强制确认，不能被“关闭逐步确认”绕过。
- 页面文本、元素文字和跳转目标仍作为不可信工具输出进入 AgentLoop；网页里的“忽略指令”等内容不能
  改写系统或用户目标。
- 历史事件最多保留 160 条，截图只保留最近 10 帧，避免长任务用 base64 截图无限占用内存；旧事件仍
  记录是否曾有截图。

### 5. 面试实战资料中的轨迹评测真正落地

- 真实浏览器事件可按 `exact`（完全一致）、`subsequence`（有序子序列）和 `any_order`（任意顺序、
  按重复次数匹配）三种模式验收，不再把普通 `fetch_url` 冒充 Browser Use 轨迹。
- UI 可填写预期动作序列并即时看到实际动作、匹配数和缺失动作；QA 模式会要求输出严重级别、复现步骤、
  预期结果、实际结果和 URL。
- 可导出 `hashmm.browser-trajectory.v1` JSON 数据集样例，包含用户目标、预期序列、匹配模式、实际动作、
  结构化事件和最终结果。导出不嵌入 base64 截图，只记录截图存在性，避免证据文件失控膨胀或意外携带
  页面像素数据。

## 仍然存在的边界

- HashMM 目前使用 Electron webContents，不是完整 Chrome 扩展；它不会自动复用用户日常 Chrome 的
  已登录 profile。需要既有企业登录态的网站仍要在隔离浏览器里单独登录。
- 站点策略按精确 host 管理，不支持通配域名。跨子域会再次询问；这是减少静默扩权的安全取舍。
- Browser Use 依赖 DOM 可交互树和截图。复杂 canvas、远程桌面流、验证码和反自动化页面可能仍需通用
  Computer Use 或人工接管。
- `browser_use` 任务需要桌面 runner 在线且 Computer Use 模型配置完整；当前 UI 会显示队列状态，但尚未
  在任务表单内完成模型配置向导。
- 轨迹匹配证明动作序列满足预期，不等于网页业务结果一定正确；最终 QA 仍需结合页面证据、结果断言和
  必要的人工复核。
- SHA-256 只能证明最终安装包字节完整，不能替代 Authenticode 发布者身份。

# HashMM V706 本轮说明

## 故障

V705 在新数据库和完整测试环境中通过，但覆盖部署到一份旧服务器数据库时，旧 `tool_approval_requests` 表没有 `work_run_id`。SQLite 的 `CREATE TABLE IF NOT EXISTS` 不会给既有表补列，而 `_SCHEMA` 又先执行了依赖该列的 `idx_tool_approval_run`，导致正常迁移函数尚未运行就启动失败。

## 修复

- `db.init_db()` 在执行 `_SCHEMA` 前检查既有内部表。
- 若审批表已存在，则以加法式迁移补齐 `work_run_id`、`step_id`、`call_id` 和 `scope_json`。
- 随后再执行完整 schema、索引和常规迁移。
- 不删除、不重建审批表，不修改旧审批的用户、会话、工具、状态或时间；旧行的新字段使用安全空默认值，不会被误认成已绑定到某个 WorkRun。

## 验证

- 回归测试从旧审批表 DDL 和一条既有审批记录开始，而不是只验证空白新库。
- 验证服务初始化成功、旧记录保留、4 个兼容列存在、运行索引建立。
- 后端完整测试：`1616 passed, 8 skipped`；两个警告均为依赖弃用提示。
- 前端：54 个测试文件、201 项测试通过；TypeScript 检查和 Next.js 生产构建通过。
- MCP 6 项通过；source-only 门禁确认 Desktop `1.42.6`、Backend `V706`、内置运行时和 WebUI 有效。
- 最终服务器包继续执行 ZIP 清单、敏感目录排除、独立 SHA-256 和直接导入门禁。

## 部署

不要继续使用 V705 ZIP 覆盖服务器。使用 V706 ZIP 解压覆盖程序文件，但保留服务器自己的 `.env`、数据库和数据目录，然后重新运行启动脚本。迁移由启动过程自动完成，不需要手工执行 SQL，也不要删除现有 SQLite 数据库。

本轮仍只交付服务器 ZIP 与桌面源码一致性验证，不声明已经生成或签名新的 Windows 安装器。

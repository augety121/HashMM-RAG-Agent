# 本轮说明 · V341（2026-07-17）—— 让 RAG-Agent 的每条主张真正回到证据

本轮继续按用户上传的四份资料审计桌面 Chat 主链，重点落实“面试实战”资料中关于可追溯性、检索评测、
错误归因和避免幻觉的细节。后端迭代号为 **V341**，桌面端、MCP client/server 与原生安装器身份版本为
**1.14.0**；MCP wire protocol 沿用项目当前真实支持值，没有用产品版本冒充协议版本。

## 本轮解决的真实缺口

### 1. 不再只展示来源列表，而是保存逐主张证据账本

此前 Chat 可以展示来源，但无法回答“答案中的哪一句由哪一段证据支持”。V341 新增统一
`grounding_ledger`，在 assistant 消息保存前对回答原文做确定性解析：

- 保存每条主张在原答案中的精确 `start/end` 字符区间，不靠 UI 二次猜测句子位置。
- 保存主张引用的整轮编号，以及对应 source ID、chunk ID、document ID、页码、章节、检索分数和片段。
- 区分 `supported`、`inferred`、`unsupported`、`invalid_citation`；“来源存在”不再自动等于“主张受支持”。
- 记录覆盖率、未引用主张数、无效引用数和 `review_required`，资料不足时不伪报全部 grounded。
- `semantic_entailment_verified` 固定为 `false`。当前自动判定是显式引用加确定性词面支持代理，不冒充事实
  真伪验证或完整语义蕴含模型。

该账本已进入普通 RAG、AgentLoop、兼容 `/api/chat` 和旧流式接口，而不是只做了一个前端组件。

### 2. 多轮检索引用编号不再冲突

此前 Agent 每调用一次知识库或 Deep Search，结果都会从 `[1]` 重新编号；同一轮多次检索后，最终答案里的
`[1]` 无法唯一定位来源。V341 把引用编号提升为整轮全局命名空间：

- Deep Search 先返回结构化 sources，再由兼容格式化层生成模型可读文本。
- 深检索预取证据先占用全局编号；后续知识库/Deep Search 工具结果按当前最大编号整体平移。
- AgentLoop 累积所有实际执行过的检索来源，跳过 guard 拒绝和去重短路结果。
- 最终 SSE `done` 事件返回真实 sources 与 groundings，不再写死空来源数组。

新增回归用真实 AgentLoop 跑通“预取 `[1]` + 工具局部 `[1]` → 全局 `[2]`”链路，并核对最终 token 与
source ID 一致。

### 3. 证据关系真正持久化并能同步

- SQLite `messages` schema 升至 v12，新增 `groundings` JSON 列；创建、更新、读取和云导入全部接线。
- Supabase push/pull/backfill 同步该字段；远端旧表缺列时回退 legacy payload，不能因一次 schema 演进
  丢掉整条消息。
- 新项目 SQL 与既有项目增量迁移都已补齐：`sql/hashmm-supabase-sync.sql` 与
  `sql/hashmm-grounding-ledger.sql`。
- 对外 sources 经过统一裁剪，只持久化 UI/审计需要的元数据，不把内部大对象或无限片段塞进消息。

### 4. Chat 里可以审阅，而不是去孤立面板找

消息气泡内新增可折叠“证据审计”卡，直接显示覆盖率、待复核状态、逐主张原文、来源、页码、片段和词面
重叠依据。流式完成后 ledger 会随消息进入前端状态，刷新历史会话后仍可重放。卡片固定展示限制声明：
证据关联用于可追溯审计，不等同于事实真伪或语义蕴含证明。

## 已知边界

- 当前自动支持判定是保守、可复现的确定性代理，不是自然语言事实核查器；需要高风险结论时仍应人工查看
  原文，或后续接入独立、可校准的 NLI/LLM judge 并保留 judge 版本与原始输出。
- 没有显式编号引用的旧回答不会被系统臆造来源关系；账本会标记不可评估或待复核。
- Supabase 既有项目需要执行 `sql/hashmm-grounding-ledger.sql` 才能原生保存新列；未迁移期间客户端会保留
  legacy 消息同步，但远端不会拥有逐主张账本。
- SHA-256 是字节完整性证据，不是发布者身份。公网安装包必须再加 Authenticode 证书和可信时间戳。

# Actions 与 Tunnel 的版本管理边界

这是一份通用流程说明，不包含可直接部署的工作流或真实环境配置。文中的 `app.example.com`、`ORGANIZATION/PRIVATE_REPOSITORY` 和 `/path/to/...` 都是占位符。采用前应按自己的仓库、托管方式和授权范围核对。

## 公开与私有内容分开

公开仓库适合保存通用 Actions、公开项目的测试流程、配置结构说明，以及不含真实资源标识的示例。历史公开源码可以继续保留；后续改为私有维护不意味着应把新的私有源码同步回来。

私有仓库保存应用源码、受控部署配置、真实服务映射、变更审查与必要验收记录。私有仓库也不应保存明文密钥、访问令牌、会话 Cookie、用户数据库或完整生产日志。秘密通过适用的受限运行时机制注入，不写入源码、构建输出或命令回显。

将私有源码送入另一仓库的 runner 是一次独立的数据处理操作。仓库名、工作流可见性和 runner 类型都不能替代该目的地的明确授权。确需使用公开仓库承载通用构建流程时，必须另外核对运行器能接触的数据、日志可见性、临时文件和产物上传边界；不能因为流程文件是通用的就公开应用源码。

## Git 描述期望状态，控制面保存实际状态

不同隧道管理方式有不同配置来源：

- 本地管理的隧道可使用本地配置文件；示例中的凭据文件路径只是引用，不应包含凭据内容。
- 远程管理的隧道从服务商控制面取得配置。连接器使用 token 文件启动，不代表仓库里的 ingress 示例会自动应用到该隧道。
- DNS、访问策略、Worker 路由、服务绑定和已部署版本分别具有自己的生命周期。

因此，`git revert` 只恢复仓库文件。除非另有经过授权且已验证的部署流程执行相应动作，否则它不会回滚云端配置、已运行进程、生产数据库或其他状态存储。

## 受控 Actions 的最小职责

1. 让普通 PR 验证使用不含生产秘密的测试数据；不要给不受信任的 PR 代码部署凭据或生产宿主权限。
2. 固定待构建的完整提交，明确源码仓与目标环境。复用已有发布校验，不以分支名或同名版本代替构建来源。
3. 将验证、构建、发布和激活分成可观察的阶段。前一阶段成功不自动证明后一阶段已执行。
4. 权限按实际任务最小化；部署身份与开发者个人登录分开。不要将生产服务器注册为执行任意 PR 代码的 runner。
5. 对每个部署目标串行处理变更，避免两个运行同时切换同一服务。取消工作流不等于生产操作已经撤销，需查询原操作结果。
6. 只上传已允许公开的输出。私有构建需要对上传内容、日志及诊断单独检查；如采用加密产物，解密材料不得与密文一同公开。

以上是流程约束，不表示任何 GitHub Environment、身份、runner 或自动部署已经配置完成。

## 变更前留下可用的恢复依据

每次实际操作先记录目标环境、当前版本、计划修改范围和恢复入口。云端配置应从实际控制面读取，不能把旧文档或本地模板当作备份。

| 对象 | 变更前保留 | 恢复后确认 |
|---|---|---|
| 应用服务 | 固定来源、旧成品、原配置引用、数据兼容性及一致性备份 | 实际运行版本、本地健康、适用认证业务 |
| Tunnel ingress | 实际配置版本或经核对的快照 | 目标映射、连接器状态、对应公网路径 |
| DNS 与访问策略 | 当前记录和规则、目标引用；敏感身份条件单独受限保存 | 实际规则、授权允许与拒绝行为 |
| Worker | 原部署版本、路由与适用绑定 | 运行版本、路由、绑定以及功能结果 |
| 数据及状态存储 | 备份、迁移和旧版本读写兼容性 | 数据完整性、权限事实和新旧服务兼容性 |

没有版本编号的控制面可以保存经核对的快照，但应明确它是快照。不要编造版本号。完整敏感备份留在受限位置，公开说明只保留通用步骤。

## 执行与回退

写入前重新读取目标，确认没有出现他人的有效修改。仅应用已授权范围，保留实际操作回执；结果未知时先查询原操作，不重复提交相同变更。

服务升级优先使用独立候选目录和现有监督器。预检通过、备份就绪后，核对监听者的进程身份和工作根，再经原服务管理入口正常停止；确认退出后启动候选。不要按宽泛进程名称批量终止服务，也不要同时运行第二份实例争抢同一端口或数据目录。

回退是一次新的受控变更：确认当前状态、后续修改和数据兼容性，再恢复适用的旧版本或规则。恢复代码不自动恢复数据，恢复 Worker 不自动恢复 DNS/访问策略，恢复旧配置也不应重新启用已撤销的秘密。需要恢复数据库时先备份当前数据，不能直接抹去升级后产生的有效记录。

## 分层验收

分别记录源码审查、构建完成、控制面写入、实际运行、本地健康、公网路由、认证业务和恢复测试。

匿名请求被访问策略拒绝，可能是正常保护；这不证明用户已经通过认证。HTTP 路由可达不等于 WebSocket、业务执行或跨设备流程正常。连接器在线不等于所有域名和策略配置正确。服务端探测与用户浏览器也可能处于不同的网络或访问策略下。

遇到故障先依据必要状态和错误码定位失败层，不因一个公网探测失败就反复重启已连接的服务。只有实际执行并取得对应证据，才把该层记录为完成。
